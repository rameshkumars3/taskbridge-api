# TaskBridge Notification and Audit Specification

## 1. Purpose and scope

This specification defines the immutable audit trail and user-facing notification behavior for TaskBridge project lifecycle events. It is intentionally scoped to the current product intent and the remediation already applied to the Project slice: tenant-scoped access, explicit validation, service-layer authorization, and transaction-safe persistence. The design covers project create, status transition, milestone reopen, and delete events and the read model required for auditing and notification review.

### In scope
- Immutable audit records for project lifecycle events.
- User notifications for relevant project activity within the same organisation.
- Retrieval and filtering endpoints for audit entries and notifications.
- Enforcement of organisation isolation and trusted identity resolution.
- Transactional consistency between project persistence and side-effect records.
- Validation, authorization, and error handling consistent with the existing project API patterns.

### Non-goals
- No milestone lifecycle beyond reopening a completed project to active.
- No exposure of actor IP addresses in the public audit response.
- No notification delivery to external channels such as email, SMS, or push.
- No soft-delete or archive policy for projects beyond the existing project lifecycle model.
- No speculative features, custom roles, or new business rules that are not already implied by the remediation and product context.

---

## 2. Actors and authorization

### Actors
- Authenticated TaskBridge user with a valid organisation membership.
- Project authorizer or equivalent permission layer enforcing the current organisation and operational rights.
- Domain owner / product stakeholder for final confirmation of event taxonomy and retention.

### Authorization rules
- Every read and write path must resolve the active organisation from the trusted security context, never from a request field.
- Organisation membership and permission checks are enforced in the service layer before reading or mutating any audit or notification record.
- Users can only read audit records and notifications for their own organisation.
- Users can only mark notifications as read when the notification belongs to the authenticated user.
- Cross-organisation access is rejected as a not-found or forbidden result, consistent with the existing Project remediation.
- No client-controlled organisation or user identifiers may be trusted for access control.

## 3. Domain model

### AuditLog
The immutable audit record stores a business event generated by project lifecycle actions. It is append-only; it must never be updated or overwritten after creation.

Java type definitions:

```java
public class AuditLog {
    private Long id;
    private String organisationId;
    private Long projectId;
    private Long actorUserId;
    private String eventType;
    private String previousStatus;
    private String newStatus;
    private String message;
    private java.time.Instant createdAt;
    private String deduplicationKey;
}
```

Rules:
- `eventType` is a constrained string representing the business event; valid values are limited to the project lifecycle set defined below.
- `previousStatus` and `newStatus` are nullable for create/delete events and populated for status transitions.
- `message` is a human-readable summary and must not contain secrets or sensitive payload data.
- `createdAt` is set once at insert time and is never mutable.
- `deduplicationKey` is required for idempotent event creation and must be stable for retries.
- No `actorIp`, `ipAddress`, or similar fields are allowed.

Supported event types:
- `PROJECT_CREATED`
- `PROJECT_STATUS_CHANGED`
- `PROJECT_DELETED`
- `PROJECT_UPDATED` (only if a later product decision requires metadata-change logging; not required for the initial version)

### Notification
The notification represents a user-visible message derived from a project audit event. Notification records are mutable only for the `read` state, not for the original event data.

Java type definitions:

```java
public class Notification {
    private Long id;
    private String organisationId;
    private Long userId;
    private Long projectId;
    private String eventType;
    private String title;
    private String message;
    private Boolean read;
    private java.time.Instant createdAt;
    private java.time.Instant readAt;
    private String deduplicationKey;
}
```

Rules:
- `read` defaults to `false` when created.
- `readAt` is set only when the notification is marked as read.
- Notification content is derived from the corresponding audit event but must remain intentionally minimal and non-sensitive.
- Duplicate notifications for the same business event must be suppressed through a stable deduplication key.
- `eventType` follows the same constrained set as the audit event set, including `MILESTONE_REOPENED`.

## 4. API contracts

Unless otherwise stated, the API is versioned under `/api` and returns JSON with the standard TaskBridge error envelope.

### POST /api/audit
Creates an immutable audit entry for a project event. This endpoint is intended for server-side integration from the Project service transaction.

Request:

```json
{
  "projectId": 123,
  "actorUserId": 42,
  "eventType": "PROJECT_STATUS_CHANGED",
  "previousStatus": "ACTIVE",
  "newStatus": "COMPLETED",
  "message": "Project status moved from ACTIVE to COMPLETED",
  "deduplicationKey": "org-9|project-123|PROJECT_STATUS_CHANGED|42|ACTIVE|COMPLETED"
}
```

Validated fields:
- `projectId`: required, positive `Long`
- `actorUserId`: required, positive `Long`
- `eventType`: required and must be one of the supported values
- `previousStatus` / `newStatus`: optional for create/delete; required for status-change events
- `message`: optional but trimmed and length-limited to a safe maximum
- `deduplicationKey`: required and unique for the business event within the organisation

Response: `201 Created`

```json
{
  "id": 991,
  "organisationId": "org-9",
  "projectId": 123,
  "actorUserId": 42,
  "eventType": "PROJECT_STATUS_CHANGED",
  "previousStatus": "ACTIVE",
  "newStatus": "COMPLETED",
  "message": "Project status moved from ACTIVE to COMPLETED",
  "createdAt": "2026-09-22T15:44:12.000Z",
  "deduplicationKey": "org-9|project-123|PROJECT_STATUS_CHANGED|42|ACTIVE|COMPLETED"
}
```

### GET /api/audit/{projectId}
Returns the immutable audit history for a project within the authenticated organisation.

Query filters:
- `from`: `java.time.Instant` in ISO-8601 format; inclusive lower bound
- `to`: `java.time.Instant` in ISO-8601 format; inclusive upper bound
- `eventType`: exact event type string, case-sensitive or normalized according to the header contract

Response: `200 OK`

```json
[
  {
    "id": 991,
    "organisationId": "org-9",
    "projectId": 123,
    "actorUserId": 42,
    "eventType": "PROJECT_STATUS_CHANGED",
    "previousStatus": "ACTIVE",
    "newStatus": "COMPLETED",
    "message": "Project status moved from ACTIVE to COMPLETED",
    "createdAt": "2026-09-22T15:44:12.000Z",
    "deduplicationKey": "org-9|project-123|PROJECT_STATUS_CHANGED|42|ACTIVE|COMPLETED"
  }
]
```

### GET /api/notifications/{userId}
Returns all notifications visible to a user within the authenticated organisation.

Query filters:
- `from`: `java.time.Instant` lower bound
- `to`: `java.time.Instant` upper bound
- `eventType`: event filter using the same supported event names

Response: `200 OK`

```json
[
  {
    "id": 501,
    "organisationId": "org-9",
    "userId": 42,
    "projectId": 123,
    "eventType": "PROJECT_STATUS_CHANGED",
    "title": "Project update",
    "message": "Project 123 moved to COMPLETED",
    "read": false,
    "createdAt": "2026-09-22T15:45:00.000Z",
    "readAt": null,
    "deduplicationKey": "org-9|project-123|PROJECT_STATUS_CHANGED|42|ACTIVE|COMPLETED"
  }
]
```

### PATCH /api/notifications/{id}/read
Marks a specific notification as read by the current user.

Response: `200 OK`

```json
{
  "id": 501,
  "organisationId": "org-9",
  "userId": 42,
  "projectId": 123,
  "eventType": "PROJECT_STATUS_CHANGED",
  "title": "Project update",
  "message": "Project 123 moved to COMPLETED",
  "read": true,
  "createdAt": "2026-09-22T15:45:00.000Z",
  "readAt": "2026-09-22T15:48:11.000Z",
  "deduplicationKey": "org-9|project-123|PROJECT_STATUS_CHANGED|42|ACTIVE|COMPLETED"
}
```

## 5. Project integration and transactional behavior

Project create, status update, and delete operations are the authoritative source for audit and notification generation. The service transaction must create or update the project and emit audit records in the same database transaction. If the project save fails, the audit and notification writes must roll back with it.

### Required integration mapping
- `PROJECT_CREATED`: emitted after successful project creation.
- `PROJECT_STATUS_CHANGED`: emitted when the project status changes between valid lifecycle states.
- `PROJECT_DELETED`: emitted after a successful project delete, before the final commit.
- `PROJECT_UPDATED`: optional metadata change event; not required in the first implementation unless explicitly approved.

### Idempotency and deduplication
- Every audit and notification write must use a stable `deduplicationKey` derived from the business event.
- A duplicate retry for the same event must not create a second notification or audit row.
- The dedupe key must include organisation scope and the project lifecycle event identity; it must not depend on the client request body alone.

### Audit immutability
- Audit records are append-only and read-only after insertion.
- No PUT/PATCH/DELETE endpoint for audit records is allowed.
- The audit table must not be exposed for update or mutation beyond creation.

## 6. Validation, error handling, and tenancy

### Validation rules
- IDs must be positive (`Long` values greater than zero)
- `from` must be strictly before or equal to `to` when both are provided
- `eventType` must be one of the supported values
- A project must exist within the authenticated organisation before audit retrieval or notification creation is allowed
- Notification updates must validate that the target notification belongs to the authenticated user and organisation

### Error responses
The API must use the existing TaskBridge error envelope and centralized exception handling.

```json
{
  "timestamp": "2026-09-22T15:50:00Z",
  "status": 400,
  "error": "Validation failed",
  "message": "eventType must be one of PROJECT_CREATED, PROJECT_STATUS_CHANGED, PROJECT_DELETED",
  "path": "/api/audit",
  "traceId": "7ad4a801-9196-4fa1-b0c5-0a1e0d7f8e62"
}
```

Typical statuses:
- `400 Bad Request` for invalid filters or payloads
- `401 Unauthorized` for missing or invalid identity context
- `403 Forbidden` for cross-organisation or insufficient permission
- `404 Not Found` for missing project, notification, or audit scope
- `409 Conflict` for duplicate deduplication attempts or invalid status transitions

### Organisation isolation
- Audit retrieval and notification queries are always scoped to the current organisation.
- `projectId` lookups must be filtered by organisation before reading data.
- No organisation value may be accepted from request parameters or client payloads for access decisions.

## 7. Assumptions, Copilot contribution, and human corrections

### Assumptions
- Notification delivery is in-app only; the system does not send push or email notifications.
- The trusted identity and organisation context are already available in the Spring security principal or token claims.
- Project lifecycle status rules are `DRAFT -> ACTIVE -> COMPLETED -> ARCHIVED`, with `COMPLETED -> ACTIVE` allowed for a milestone reopen.
- Audit actor IP is captured from the server request remote address, never forwarding headers or client payloads, and remains nullable for historical rows.
- Audit and notification records are persisted in the same database as the project domain or via the same tenant-safe persistence layer.

### Copilot contribution
Copilot’s role in this slice is to draft a requirement-aligned contract that reuses the Project remediation’s tenant-safe architecture, service-layer validation, and exception conventions. The draft deliberately avoids speculative fields, unsupported statuses, and unsupported endpoint behaviors.

### Human corrections required before implementation
- Confirm the final approved event taxonomy and whether `PROJECT_UPDATED` is required for metadata changes.
- Confirm whether notifications are in-app only or whether external delivery channels are in scope.
- Confirm the final retention and cleanup policy for audit records and notifications.
- Confirm whether any additional role-specific permissions are required beyond the current organisation-scoped authorizer pattern.

Actor IP is retained only on persisted audit records and is intentionally omitted from the public audit response.
